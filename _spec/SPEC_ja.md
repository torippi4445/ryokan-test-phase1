# 設計メモ（日本語版・確認用） — 小規模旅館向け 多言語問い合わせ自動対応システム

> ※ これは確認用の日本語訳です。Claude Code に読ませるのは英語版（SPEC.md）の方。

## 1. 作るもの
小規模な家族経営の旅館が、外国（主に英語圏）からの問い合わせに対応するのを助けるデモシステム。
女将さんが外国語を読み書きする必要がなく、新しいアプリも覚えなくていい。

女将さん（高齢でITが苦手な想定）は **LINE上で日本語のみ** でやり取りする。
言語の壁は全部システムが裏で吸収する。

これはまず「営業で見せるためのデモ」。架空の旅館のデータで端から端まで動くことが条件。

## 2. 想定ユーザー（作る間ずっと具体的に保つ）
- 馬籠〜妻籠（中山道・岐阜／長野）の小規模旅館・民宿。
- 客：欧米系の個人客（FIT）、問い合わせは英語。
- 女将さんは英語も新しいソフトも苦手。
- 宿はすでに OTA（Booking.com／Airbnb）に出していて、メールも使っている。

## 3. 技術スタック
- **n8n**：ワークフローの司令塔。
- **Claude API**：理解・翻訳・要約・返信下書き。
- **LINE公式アカウント＋Messaging API**：女将さんとの双方向のやり取り。
- メール（IMAP／Gmail）：問い合わせの入口。

## 4. 入力チャネル — 重要な制約
OTA内のメッセージを直接読みにいこうとしない。Booking.com／Airbnb のメッセージは
各プラットフォーム内に閉じていて、外部から扱うには公式のAPI連携（コネクティビティ・
パートナー登録）が必要。デモ段階の個人には現実的でない。

代わりに **メールを唯一の入口** として扱う：
- 客からの直接メール、および
- OTAからの「新着メッセージあり」の通知メール（宿のメールボックスに届く）。

n8nがそのメールボックスを監視し、送信元・件名でOTA由来か直メールかを見分ける。
これは実際の宿の運用に近い。

## 5. コア設計 — 3色トリアージ（システムの心臓部）
すべての問い合わせを3段階に分類する。**この振り分けは事前に決めたカテゴリのルールで行う。
AIに「簡単か難しいか自由に判断して」とは絶対にやらせない。** 人間（運用者＋女将さん）が
事前に線を引き、AIはその線に沿って分類するだけ。

- **緑 — 完全自動**：答えが固定で、間違えても実害が小さいもの。
  例「駐車場はありますか」「チェックインは何時」「Wi-Fiはありますか」「駅から何分」
  → AIが訳し、FAQから答えて自動送信。女将さんは事後にログを見るだけ。

- **黄 — AI下書き → 女将さん承認**：答えはあるが、金額・在庫・約束が絡み、間違うと困るもの。
  例「12月24日空いてますか」「2名1泊いくら」「アレルギー対応できますか」
  → AIが下書きを作り、女将さんがLINEでOKを押して送信。

- **赤 — 最初から女将さんへ**：個別事情・交渉・クレーム・イレギュラー。
  例「車椅子の祖母と泊まりたいが館内は大丈夫か」「予約を変更したい」「到着が深夜になる」
  → AIは訳して要約するだけ。答えは書かない。女将さんが判断。

### 安全ルール（外さないこと）
1. 振り分けはカテゴリのルールで。AIの自由な難易度判断に任せない。
2. **黄・赤では、客に送る前に必ず人間の確認を挟む。** 緑だけは事前承認済みの
   固定カテゴリに限り自動送信。
3. 最初は安全側に倒す：迷ったら黄か赤へ。確実に定型だと分かったものだけ、女将さんと
   相談して緑に降ろす。見栄えのために最初から緑を増やさない。信頼は事故ゼロの実績で積む。

## 6. 言語フロー
外国語の問い合わせ
→ Claudeが日本語に要約（客が何を聞いているか）
→ 女将さんのLINEに日本語で届く
→ 女将さんがLINE上で日本語のまま返信
→ Claudeがそれを元の言語に翻訳
→ 「この内容で送ります、OKですか?」と確認がLINEに出る
→ OKで、元の言語のまま客へ送信。

女将さんの体験は「LINEに来た日本語の質問に、日本語で答えて、OKを押すだけ」。
言語処理は全部見えないところで完結する。

## 7. 作る順番（最初から全部を双方向で作らない）
**第1段（まず作る）：一方向。**
外国語問い合わせ → 日本語要約＋返信下書き → 運用者自身のLINEかメールに届く。
女将さん側のLINE入力はまだ無し。これだけで「言語の壁を溶かす」価値は見せられ、
営業の見本として十分。

**第2段（次に足す）：双方向。**
女将さんが日本語で返信 → 翻訳 → 確認 → 送信。LINE Messaging APIの双方向設定が
必要なので後回しにし、LINE連携で最初に時間を溶かさない。

## 8. 必要なデモ用データ
架空の旅館プロフィール＋FAQ（駐車場、チェックイン/アウト時刻、アクセス、Wi-Fi、
設備、食事/アレルギー、キャンセルポリシー）。緑の自動回答と黄の下書きに使う。
よくある問い合わせを緑/黄/赤に対応づけた振り分け表が、次に作るもの。
